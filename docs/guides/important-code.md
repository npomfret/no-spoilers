18. `scripts/verify-core-tests.sh` — canonical Swift package test wrapper. `scripts/verify-python-selftests.sh` is its counterpart for the Python: six scripts carry an offline `--selftest`, they share a key and an app record, and until 2026-08-22 there was no way to run them together.
19. `scripts/verify-mac-build.sh`, `scripts/verify-ios-build.sh`, `scripts/verify-widget-build.sh` — canonical Xcode build wrappers. **These three and 18 are now also the CI job**: since 2026-08-25 `ci.snowmonkey.co.uk` runs all five as the `No Spoilers` project — `Checks` (18's Python half), `Build` (these three as one configuration), `Tests` (18's Swift half) and `Verdict`, which runs nothing and exists so one light answers "did this commit pass". That is only possible because each wrapper already redirects `HOME`, `XDG_CACHE_HOME` and the module caches into the repo's `tmp/` and passes `CODE_SIGNING_ALLOWED=NO` — the agent needs Xcode and a checkout, not a keychain, so **nothing about the CI path may be allowed to reintroduce a credential into these five**. It builds the public GitHub remote anonymously for the same reason. `Verdict` is the chain's only VCS entry point and carries a nightly schedule trigger at 00:00 Europe/London, and its three snapshot dependencies deliberately set `take-started-build-with-same-revisions=false`. Those are one decision, not two: without the flag a nightly at an already-built revision reuses the last green chain and reports success having compiled nothing, and with it a second trigger on any leaf configuration builds the whole chain twice — both were measured. `Build` and `Tests` hold *read* locks on `no-spoilers-xcode`, so they run beside each other, and that resource is project-scoped, so another project on the same Mac can compile alongside ours. The server is the record for that configuration and this repo holds none of it: provisioning ran from throwaway scripts against `/app/rest` over an SSH tunnel, using an access token that is full-admin scope and belongs in no repository, so **nothing here may ever read it** — the server's own `TEAMCITY-AGENTS.md`, in the `snowmonkey-proxy-common` repo, is the operational reference. Revisit all of it the moment anything here drives a simulator in CI: the agents' recurring `posix_spawn failed` wedge, which turns every project on the server red at once until they are restarted, traces to leaked simulator processes on that machine.
20. `scripts/release.sh` — the single release engine; `scripts/ship-*.sh` are the only wrappers over it. `.github/workflows/release.yml` was deleted on 2026-08-12 having never once succeeded. **Since 2026-08-25 there is one CI release path and it is 39, which is a preflight rather than a second engine.** It gained `--signing-key/--signing-key-id/--signing-issuer`, forwarded to `xcodebuild` as `-authenticationKeyPath` on both the archive and the export, for a machine with a certificate and no Xcode account; omitted, they expand to nothing and the local path is unchanged. The five verification configurations in 19 still hold no credential and must not gain one; publishing is a separate configuration that runs only when a person presses it, and only on a revision `Verdict` has already passed. **Its preflight is where correctness lives**: it refuses a dirty tree, refuses a checkout behind its upstream, takes the build number from App Store Connect (`next_build_number` in `_version.sh`, over 22's `--next-build`, or the highest `build/` tag if that is higher), refuses a `(version, build)` pair App Store Connect already holds or a version whose train is closed, refuses a pinned `--build` whose `build/` tag is on another commit, and runs 18 as the release gate — the same gate 21 applies, in the path that now does the shipping. All of it runs before anything is edited, built or uploaded. **The upstream check is an ancestor test, not an equality one** — being ahead is the normal laptop flow and is allowed; only work the checkout has not seen is refused, because `main` is pushed with a bare `git push`. **Since task 32 (2026-09-05) a run leaves an `open vX.Y.Z` commit only when the version changed, pushed before the archive with a rebase-and-retry (three attempts, for the commit that lands mid-run and which no preflight can catch), and an annotated `build/N` tag on the commit it archived, pushed the moment the archive exists.** The `bump to vX (build N)` commit and its `Built-From:` trailer are gone: pushing first means `HEAD` is final before `xcodebuild` reads the tree, so the tag says what was built and nothing has to be inferred. Before the tag it checks every `.app` and `.appex` in the archive reads `CFBundleVersion` N, because the number now reaches the build from the `xcodebuild archive` command line alone and an app whose widget extension disagrees is refused at upload. It no longer calls `set_build_number`; the committed `CURRENT_PROJECT_VERSION` is frozen at 10022. It tags `vX.Y.Z` on the Developer ID channel only, annotated, because the Homebrew cask downloads by that name; the App Store channels tag no version — 41 does that at approval. `set_marketing_version` still proves its work against the file afterwards, because a `sed` succeeds having matched nothing.
21. `NoSpoilers/ci_scripts/ci_pre_xcodebuild.sh` — the only Xcode Cloud hook: the test gate and the build-number stamp for the iOS TestFlight path. The stamp is `set_build_number` from `scripts/_version.sh`, of which this is the only caller since task 32; it stays in `_version.sh` because it is the careful implementation and 20 once carried a careless copy. See `docs/guides/building.md`.
22. `scripts/appstore_status.py` — reads App Store Connect and TestFlight for **both platforms**, writes nothing. Holds everything the Python here shares: ES256 token signing (`token`, `key_path`), the app lookup (`find_app`), build selection (`builds_path`, `platform_builds`, `live_builds`, `newest_build`, `groups_holding`), the platform pair (`PLATFORM_FLAGS`, `TESTFLIGHT_PLATFORMS`), and the Xcode Cloud product lookup (`ci_products`, `select_ci_product`, `find_ci_product`). Four one-question flags serve the shell: `--spent PLATFORM VERSION BUILD` for 20's preflight (0 free, 3 taken), `--train PLATFORM VERSION` for 39 (0 open, 3 closed), `--next-build` for `_version.sh`'s `next_build_number` (the highest build on either platform plus one, on stdout), and `--approved PLATFORM VERSION` for 41 (the approved build's number on stdout, 3 not on the store). In every case anything else means the check did not run, which is a distinction a release script has to be able to make. `highest_build`, `store_version`, `closed_train` and `approved_build` are the helpers behind them. Newest means most recently uploaded, never the highest number — define it once here, not twice. The owned-terms scan under NEEDS YOU asks **two** questions and not one: whether the copy this version would ship carries a mark, and whether the public page carries one *now* — `name` and `subtitle` belong to the app rather than the version, so a staged fix for either waits on an approval. Merging the two was how `No Spoilers F1` stayed the live name while the report read clean.
23. `scripts/testflight_distribute.py` — TestFlight delivery: hands one platform's newest build to a tester group and makes that build's *What to Test* note describe it — from the Xcode Cloud run that produced it, or, for a locally shipped build that no run produced, from the `build/N` tag 20 writes on the archived commit; for builds 10001–10022, which predate the tag, from the `bump to vX.Y.Z (build N)` commit via its `Built-From:` trailer, falling back to its parent for the bump commits written before 20 learned to rebase on 2026-08-26. `ship_commit` is that lookup, and 41 imports it rather than repeating it; `git` beside it takes a `repo` so the selftest can exercise the tag path in a throwaway repository. It fetches tags before asking, because the tag was pushed by whichever machine shipped. It imports 22's selection helpers rather than repeating them, so the report and the command cannot disagree about which build is newest, and its `--platform` choices **are** 22's `PLATFORM_FLAGS`, so a platform it can deliver to is one the report covers. The read/write split is deliberate: 22 reads and never writes; 23, 33, and 40 all require `--apply` and share the App Manager session in 32.
24. `scripts/ci_health.py` — read-only check that Xcode Cloud is wired to the right projects, and the thing to run immediately after Integrate → Create Workflow. Two projects share this Apple team, and that wizard has three times seized the other one's product; see the Continuous delivery section of `docs/guides/building.md`. It asserts non-interference in both directions — no product of ours attached to another repository, and **no product of theirs attached to ours**.

25. `scripts/screenshots.py` — the only thing that produces App Store listing screenshots. Seeds a fixture into the App Group container, places the widget at a chosen family, boots and captures. It writes to a simulator and to `tmp/screenshots/` and **never to App Store Connect**; 40 owns upload. Stdlib-only like the rest of the Python here. **A newly created simulator must launch the app once before its first capture so WidgetKit registers the extension; the app is never launched during the capture sequence.** `ScheduleStore.refresh()` fetches and calls `cache.save(...)` unconditionally, so launching after the fixture is seeded destroys it. **That is not the only way it dies**: `ScheduleSnapshot` falls back to the network on a cache miss and writes what it fetches back, so a device seeing the widget for the first time replaces the fixture with the live calendar without the app ever running — `confirm_fixture_intact` is what catches it. It covers `small`, `medium`, `large` and `extraLarge`; `extraLarge` is iPad-only and is why `NoSpoilers-iPad` exists. **Build the app for the simulator without `CODE_SIGNING_ALLOWED=NO`** — that flag is in `verify-ios-build.sh` and is right there, but it strips the entitlements, so the App Group container is never created and this script dies at `simctl get_app_container … group.pomocorp.no-spoilers` with exit 117 and a usage message that says nothing about signing. Found on 2026-08-26 photographing the wordmark. **The Lock Screen families are not placeable from here and cannot be made so.** The Home Screen works because `IconState.plist` is SpringBoard's own declarative layout, read on boot; the Lock Screen has no such file. Placement lives in chronod's `chrono.sql` under host `::Complications`, but that table is *derived* from state PosterBoard owns, and reconciliation prunes any descriptor written into it — one was written, survived the boot, rendered nothing at every `location`, and was gone on the next read (established 2026-08-24). The only other route is synthetic clicks on the real desktop, which must not be added here. If a Lock Screen listing shot is ever needed, add the widget by hand once on `NoSpoilers-iPhone`; the configuration persists on that device and seed/reboot/lock/capture is ordinary tooling from there. `Device ▸ Lock` does not respond to AppleScript either — a person pressing ⌘L is what produced the one Lock Screen capture. See `docs/guides/building.md` and the script's own docstring, which is the long-form reference.

26. `docs/guides/brand.md` — **the cross-platform token spec**, and the authority for any visual decision. Every token with both its bindings, and an explicit note on the Swift-only families. Moved here from `docs/brand.md` on 2026-08-17, where it had been a colour-only document that the code had drifted from.
27. `NoSpoilersCore/Sources/NoSpoilersCore/Theme.swift` — the Swift binding of 26. `Palette`, `Canvas`, `Typography`, `Space`, `Radius`, `Motion`, `Icon`, plus the per-component families (`Card`, `MessageCard`, `Badge`, `Row`, `NextUp`, `Header`, `ScreenHeader`, `SectionLabel`, `DetailRow`). **`Theme.Canvas` is the only size axis** — `iosApp`, `macPopover`, `widgetSmall`, `widgetMedium`, `widgetLarge`. Do not add a second one; a `NoSpoilersCardDensity` and a `compact: Bool` both existed beside it and both are deleted. Its doc comments carry the reasoning behind each value and are worth reading before changing one.
28. `NoSpoilersCore/Sources/NoSpoilersCore/BrandPalette.swift` — the only place a colour hex lives on the Swift side. `Theme.Palette` names roles that point at it. **`signalRed` is also transcribed into three `AccentColor.colorset` JSON files**, because an asset catalog cannot reference Swift and nothing will fail to compile if they drift.
29. `NoSpoilersCore/Sources/NoSpoilersCore/SharedChrome.swift` — the shared components every target draws, and the boundary duplicated views converge onto rather than being reimplemented beside. A second implementation of anything here is a correctness issue, not a style one.
30. `scripts/alerts_check.py` — the only way to see whether the iOS session alerts reach the OS. Launches the app on the simulator and streams the `alerts` log channel back, reporting planned against pending. **Imports its device helpers from 25** rather than repeating them, the same way 23 imports 22's: two scripts that disagree about which simulator they mean is the failure this prevents. Its `--push` sample copy is *extracted from* `Strings.Alerts` in `NoSpoilersCore`, never transcribed — a second copy of notification wording would drift and still screenshot convincingly. It cannot fire one of our own alerts on demand, and its docstring carries the reason: a seeded fixture does not survive `ScheduleStore.refresh()`, and the seam that would fix it is 25's declined launch-argument trade.
31. `docs/styles.css` — the CSS binding of 26, shared by `docs/index.html` and `docs/privacy.html`. Neither page may carry its own `:root` block, a raw hex, or a raw radius.
32. `scripts/asc_write.py` — the App Store Connect session that writes, and the App Manager key id, spelled once. Split out of 23 on 2026-08-22 when it stopped being the only writer; it holds no token signing and no app lookup, because those are 22's and a second implementation of ES256 is a second thing to get wrong. Its two invariants — a 403 hint that names the key, and a write key that is not the read-only one — are asserted in 23's selftest.
33. `scripts/appstore_listing.py` — writes an App Store version's listing from `listing/<platform>/*.txt`, which is where the app's own description, keywords, promotional text, what's-new and review notes now live. **Before this the listing existed nowhere but App Store Connect**, which is how the macOS keywords kept `F1,Formula 1` for nine days after the sweep that was meant to remove them: the sweep edited four surfaces by hand and there was no fifth place to look. It refuses to write copy carrying the owned terms, using 22's `trademark_hits` — the same check 22 reports under NEEDS YOU, so a listing cannot pass here and be flagged there. It creates the version record, writes the four fields and the review detail, and attaches a build. **It never submits**; a READY_FOR_SALE version is not even a candidate, so it cannot rewrite words that are already on the store.
34. `scripts/mac_screenshots.py` — the macOS listing screenshot: drives the installed app, clicks the status item through System Events and captures a top-right region of the real screen. **It no longer seeds a fixture.** It did, and the sandboxed Mac app could neither read nor replace a file an unsandboxed script wrote into its group container — so the seed was invisible and it displaced the cache the app maintains, which then failed to load and failed to save for a day before anyone read the log. Making it work needs the app to be told what to hold, which is the offline seam 25 declined to open. **It refuses two things**, both learned by doing them: photographing a build that is not the one this checkout makes — the first run captured the installed 1.0.21 and produced a perfect screenshot of the wordmark deleted for 4.1(a) — and running with the feed reachable, which makes the picture one of today rather than of the fixture. Which data it captured comes from the app's `store` log channel, not from reading the cache back, because that was wrong on both of the first two runs. `--appearance dark` flips the system appearance around the capture and restores it in a `finally`, because a menu bar app has no per-app override and the popover follows the Mac since task 28.

35. `NoSpoilersCore/Sources/NoSpoilersCore/FeaturedSession.swift` — **the one answer to "what is on, or on next"**: the session running, or the next to start. Third planner in the shape of 27's neighbour `TimelinePlanner`, after `SessionAlertPlanner`, and pure for the same reason — `now` is a parameter, so every decision is assertable. It computes no boundary of its own; `ScheduleBoundaries` is the single traversal and `SessionResolver` the single answer to when a session starts and is over. **Two callers, deliberately one implementation**: the Live Activity and `NextSessionIntent` both say this sentence, one on a Lock Screen and one out loud, and two functions computing it would be two answers a user could catch disagreeing on the same device. `lookAhead` is caller-owned because the two genuinely differ — 8 hours for an activity, `.infinity` for an intent — the same split that puts `maxEntries` in the widget and the 64-notification cap in the scheduler.
36. `NoSpoilersCore/Sources/NoSpoilersCore/ScheduleSnapshot.swift` — the App-Group-cache-then-network read, for the processes that wake up with nothing in memory. Was `resolveWidgetData`, private inside `NoSpoilersWidget.swift`, for as long as the widget was the only such process; the App Intent is the second, and a copy beside the original would have been two answers to where the schedule comes from. `ScheduleStore` is the app's path and stays separate: it publishes, refreshes on a timer, and belongs to a process with a lifecycle. **It writes a successful fetch back to the cache**, which is the trap 25's `confirm_fixture_intact` exists to catch.
37. `NoSpoilers/NoSpoilersWidget/SessionActivityWidget.swift`, `NoSpoilers/NoSpoilers/SessionActivityController.swift` and `SessionActivityAttributes.swift` in Core — the Live Activity. The attributes type is in Core because ActivityKit matches a running activity to its configuration by type identity, so the app and the extension must share one declaration; a copy in each compiles and never renders. The controller is thin for the same reason `SessionAlertScheduler` is — every decision is in 35 — and is `#if os(iOS)` on the Core side because the package builds for macOS too. **No entitlement, but there IS a prompt** — this entry said otherwise until 2026-08-25, when the first activity anyone looked at arrived under *"Allow Live Activities from No Spoilers?"* on the Lock Screen. iOS asks on the first activity and nothing in the API says it is about to, so this is the notification permission again one feature later: a Don't Allow leaves `areActivitiesEnabled` false, `refresh` returning having done nothing, and the feature inert while every log line reads as normal. The controller now publishes `activitiesEnabled` and `SessionAlertsView` draws an off-notice in the same shape as `SessionAlertSettingsRows.deniedNotice`, because a silent refusal is the defect, not the refusal. There is still nothing to *request*: the prompt is iOS's own and a refusal is reversible only in Settings. `NoSpoilersApp.entitlements` still carries only the App Group, and only push-to-start would need more. The app target gains `INFOPLIST_KEY_NSSupportsLiveActivities`.
38. `NoSpoilers/NoSpoilers/NextSessionIntent.swift` — the App Intent behind Siri, Spotlight, Shortcuts and the Action button, plus the `AppShortcutsProvider` that makes it discoverable without the user opening Shortcuts first. **Its install-time copy is the one exception to the strings rule**, and not by choice: `appintentsmetadataprocessor` extracts the title, description, short title and phrases at build time and fails the build on anything that is not a literal at the declaration site. Those four are inline with a comment saying so, and `Strings.Intents` carries a note pointing at them; what the intent says at *run* time is not extracted and lives in `Strings.Intents` with everything else. Verify extraction by reading `Metadata.appintents/extract.actionsdata` out of the built `.app` — "Extracted no relevant App Intents symbols" in the build log means the intent is not there.

**The Resolution Center is not in this repo.** 22 reports a submission's state and cannot read why it was rejected or answer it; that is `/Users/nickpomfret/projects/appstoreconnect-bot`, a sibling repo whose `report`, `save-draft` and `send-reply` commands drive Apple's private `iris` service on a browser cookie. The two are deliberately separate credentials and neither grows the other's job.

**Never identify an Xcode Cloud product by name or by a recorded id.** The name is the field the fault rewrites, and the id does not survive a deletion — a constant id took 23 down entirely, dry run included. `find_ci_product` matches on the app the product builds, which is the field the fault strips rather than forges, so a seized record matches nothing instead of matching wrongly.

## Update rule

When core architecture or canonical patterns change, update this guide so Claude has an accurate map of the approved structure.

39. `scripts/ci-publish-ios.sh` — the TeamCity entry point for an iOS TestFlight upload, and **deliberately thin**: it asserts three things, chooses a version, and then `exec`s `scripts/ship-ios.sh`. 20 is the one release engine and this is not a second one. **Given no version it ships the project's while App Store Connect is still taking builds for it and the next patch version once that train is closed** (`appstore_status.py --train`, then `suggest_next_version`), since 2026-09-05, because a button pressed with its parameter empty has to work the day after an approval as well as the day before; 20 itself still ships exactly the version it is told. **A closed train is also where the approval is recorded**: before opening the next version it runs 41 for the closed one, so `ios/vX.Y.Z` is written by the first press after Apple approves, and `--check` dry-runs that too. The three are what 20 reasonably assumes about a laptop and which are all false by default on a build agent. **It signs a throwaway binary rather than trusting `security find-identity`** — a locked login keychain lists its identities happily and then refuses to sign with `errSecInternalComponent`, measured on `macstudio.local` over SSH, so the listing answers a different question that looks the same in a green log. **The agents' own session is unlocked and signing works there** — build 705 on 2026-08-25 proved it, which is the fact the whole CI release path rests on and the one nothing outside a build can establish. `--check` runs the three assertions and stops; run it on a new agent, after an OS update, and after anything touches the keychain, because the alternative way to ask is to press the button that uploads to Apple and pushes a tag. It checks the App Store Connect key is on disk, because without one 20 degrades to printing manual upload instructions and exits 0, delivering nothing. And it rewrites `origin`'s push URL to SSH, because TeamCity checks out the public remote anonymously while 20 commits the version bump and pushes the tag *after* the archive exists — a push that fails there leaves an uploaded build whose number is recorded nowhere. That push uses the agent account's own GitHub key, which is unscoped and shared with everything else on that machine; a per-repository deploy key is the better answer and is not done. **It also passes 20's `--signing-key` trio**, pointing at the App Manager key `ASC6H3SL2D` rather than the upload key: automatic signing with no Xcode account falls back to the generic `iOS Team Provisioning Profile: *`, which carries no App Group, and the archive then fails naming a capability. The *export* needs a distribution profile on top of that, and minting one is cloud signing the key is refused — so the two `iOS Team Store` profiles are installed on the agent by hand and **expire in about a year**, at which point this fails as a permission error rather than an expiry. Proven end to end on 2026-08-25: iOS 1.1.2 build 10008.

40. `scripts/appstore_screenshots.py` — puts screenshots on a version, and is the last listing surface that only existed in a browser: 33 ended that for the words on 2026-08-22 while the images stayed a drag-and-drop into a web form, which is the same condition — nothing could check them, diff them, or say which build they came from. Dry-run by default and `--apply` to act, like every writer here. **The display type comes from the PNG's own IHDR, never from a filename**, because an image of the wrong shape is refused *after* the reserve and leaves an empty `appScreenshot` that counts toward the set and blocks a submission without appearing in the web form; an unmapped size stops the run before anything is reserved. Every file is read and measured up front for the same reason — with `--replace`, a bad file at the end of the list would otherwise mean a set whose old images are deleted and whose new ones never arrive. `DISPLAY_TYPES` was read off the app record rather than from Apple's documentation, which is how 25's year-old list sent two capture runs at a slot this app does not have. It does not reorder: Apple shows screenshots in upload order, so order is argument order and there is no second way to say it. `asc_write.Session.delete` exists for this and nothing else — the API has no replace, and an upload into a full set appends.

41. `scripts/tag_approved.py` — writes `ios/vX.Y.Z` or `macos/vX.Y.Z` on the commit of the build App Store Connect says is on the store, since task 32 (2026-09-05). Before it, a version tag marked the *first* upload of a train and nothing in the repository said which commit users got: `v1.1.2` marks build 10003 while 10012 is on sale. It asks 22's `approved_build` for the number, 23's `ship_commit` for the commit (`build/N`, or the bump commit for 10001–10022), and writes an annotated tag — two names, because the platforms are approved at different builds. Dry-run by default, `--apply` to tag and push, like every writer here; it reads with the Developer key because it writes only to git. **It never moves a tag**: one already on the right commit is kept, one on another commit stops the run, because a tag that moves is a tag nobody can trust. 39 runs it for iOS the moment a train is reported closed; a person runs it for macOS. The 26 bare `vX.Y.Z` tags up to `v1.1.3` are left as history, and the bare name is kept only for the Developer ID release, whose cask downloads by it.
