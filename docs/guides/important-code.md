# Important Code Guide

This guide maps the current control plane and the places that define repo standards.

## Current control plane

2. `.claude/rules/core.md` — repo-wide engineering and pattern-governance rules.
3. `.claude/rules/apple-platforms.md` — Apple-platform implementation rules.
4. `.claude/rules/testing.md` — verification and evidence rules.

6. `.claude/skills/feature-workflow/SKILL.md` — audit-first workflow for non-trivial features, bug fixes, behavior changes, and refactors.
7. `.claude/skills/implement-apple-change/SKILL.md` — implementation/refactor workflow for Swift and Apple-platform code.
8. `.claude/skills/build-verify/SKILL.md` — compile, build, and toolchain verification workflow.
9. `.claude/skills/test-changes/SKILL.md` — targeted behavior-risk verification workflow.
10. `.claude/skills/review-working-tree/SKILL.md` — read-only correctness and pattern-drift review workflow.
11. `.claude/skills/claude-setup-maintenance/SKILL.md` — workflow for maintaining Claude Code instructions and automation.
12. `.claude/agents/codebase-explorer.md` — discovery and pattern lookup specialist.
13. `.claude/agents/pattern-compliance-reviewer.md` — read-only duplication and pattern-drift specialist.
14. `.claude/rules/spoiler-safety.md` — path-scoped enforcement of the product's schedule-only, no-results contract.
15. `.claude/agents/spoiler-safety-reviewer.md` — read-only audit specialist for spoiler-risk changes.
16. `.claude/skills/release-and-delivery/SKILL.md` — explicit-only workflow for releases, TestFlight, Xcode Cloud, App Store Connect, and listing screenshots.
17. `docs/guides/claude-code-setup.md` — longer reference for the Claude Code control plane.
18. `scripts/verify-core-tests.sh` — canonical Swift package test wrapper. `scripts/verify-python-selftests.sh` is its counterpart for the Python: four scripts carry an offline `--selftest`, they share a key and an app record, and until 2026-08-22 there was no way to run them together.
19. `scripts/verify-mac-build.sh`, `scripts/verify-ios-build.sh`, `scripts/verify-widget-build.sh` — canonical Xcode build wrappers. **These three and 18 are now also the CI job**: since 2026-08-25 `ci.snowmonkey.co.uk` runs all five as the `No Spoilers` project — `Checks` (18's Python half), `Build` (these three as one configuration), `Tests` (18's Swift half) and `Verdict`, which runs nothing and exists so one light answers "did this commit pass". That is only possible because each wrapper already redirects `HOME`, `XDG_CACHE_HOME` and the module caches into the repo's `tmp/` and passes `CODE_SIGNING_ALLOWED=NO` — the agent needs Xcode and a checkout, not a keychain, so **nothing about the CI path may be allowed to reintroduce a credential into these five**. It builds the public GitHub remote anonymously for the same reason. `Verdict` is the chain's only VCS entry point and carries a nightly schedule trigger at 00:00 Europe/London, and its three snapshot dependencies deliberately set `take-started-build-with-same-revisions=false`. Those are one decision, not two: without the flag a nightly at an already-built revision reuses the last green chain and reports success having compiled nothing, and with it a second trigger on any leaf configuration builds the whole chain twice — both were measured. `Build` and `Tests` hold *read* locks on `no-spoilers-xcode`, so they run beside each other, and that resource is project-scoped, so another project on the same Mac can compile alongside ours. The server is the record for that configuration and this repo holds none of it: provisioning ran from throwaway scripts against `/app/rest` over an SSH tunnel, using an access token that is full-admin scope and belongs in no repository, so **nothing here may ever read it** — the server's own `TEAMCITY-AGENTS.md`, in the `snowmonkey-proxy-common` repo, is the operational reference. Revisit all of it the moment anything here drives a simulator in CI: the agents' recurring `posix_spawn failed` wedge, which turns every project on the server red at once until they are restarted, traces to leaked simulator processes on that machine.
20. `scripts/release.sh` — the single release engine; `scripts/ship-*.sh` are the only wrappers over it, and they run on your machine. There is no CI release path: `.github/workflows/release.yml` was deleted on 2026-08-12 having never once succeeded, and the TeamCity project in 19 deliberately verifies only — it holds no signing identity, no App Store Connect key and no push rights, so releasing stays a local run. **Its preflight is where correctness lives**: it refuses a dirty tree, refuses a `(version, build)` pair App Store Connect already holds, and runs 18 as the release gate — the same gate 21 applies, in the path that now does the shipping. All three run before anything is edited, built or uploaded. It reads and writes the project's version only through `scripts/_version.sh` — `current_build_number` and `suggest_next_version` out, `set_build_number` and `set_marketing_version` in — and both setters prove their work against the file afterwards, because `agvtool` exits 0 having changed nothing and a `sed` succeeds having matched nothing, and a build number that reaches only some configurations is refused at upload after the archive.
21. `NoSpoilers/ci_scripts/ci_pre_xcodebuild.sh` — the only Xcode Cloud hook: the test gate and the build-number stamp for the iOS TestFlight path. The stamp is `set_build_number` from `scripts/_version.sh`, shared with 20 rather than repeated. See `docs/guides/building.md`.
22. `scripts/appstore_status.py` — reads App Store Connect and TestFlight for **both platforms**, writes nothing. Holds everything the Python here shares: ES256 token signing (`token`, `key_path`), the app lookup (`find_app`), build selection (`builds_path`, `platform_builds`, `live_builds`, `newest_build`, `groups_holding`), the platform pair (`PLATFORM_FLAGS`, `TESTFLIGHT_PLATFORMS`), and the Xcode Cloud product lookup (`ci_products`, `select_ci_product`, `find_ci_product`). `--spent PLATFORM VERSION BUILD` answers one question for 20's preflight and prints nothing else — 0 free, 3 taken, anything else means the check did not run, which is a distinction a release script has to be able to make. Newest means most recently uploaded, never the highest number — define it once here, not twice.
23. `scripts/testflight_distribute.py` — TestFlight delivery, and one of the two things here that write (the other is 33): hands one platform's newest build to a tester group and makes that build's *What to Test* note describe it — from the Xcode Cloud run that produced it, or, for a locally shipped build that no run produced, from the `bump to vX.Y.Z (build N)` commit `release.sh` writes. It imports 22's selection helpers rather than repeating them, so the report and the command cannot disagree about which build is newest, and its `--platform` choices **are** 22's `PLATFORM_FLAGS`, so a platform it can deliver to is one the report covers. The read/write split is deliberate and carries a key boundary with it: 22 reads and never writes, 23 and 33 write and say `--apply` first, and the App Manager key they share is spelled once, in 32.
24. `scripts/ci_health.py` — read-only check that Xcode Cloud is wired to the right projects, and the thing to run immediately after Integrate → Create Workflow. Two projects share this Apple team, and that wizard has three times seized the other one's product; see the Continuous delivery section of `docs/guides/building.md`. It asserts non-interference in both directions — no product of ours attached to another repository, and **no product of theirs attached to ours**.

25. `scripts/screenshots.py` — the only thing that produces App Store listing screenshots. Seeds a fixture into the App Group container, places the widget at a chosen family, boots and captures. It writes to a simulator and to `tmp/screenshots/` and **never to App Store Connect**, which is what keeps it outside the read/write split above; uploading is 33's job for listing copy, 23's raw session for anything else, or the bot. Stdlib-only like the rest of the Python here. **Its central rule is that the app is never launched** — `ScheduleStore.refresh()` fetches and calls `cache.save(...)` unconditionally, with no freshness check of any kind to stop it, so launching the app to "make it pick up the fixture" is what destroys the fixture. **That is not the only way it dies**: the widget's own `resolveWidgetData()` falls back to the network on a cache miss and writes what it fetches back, so a device seeing the widget for the first time replaces the fixture with the live calendar without the app ever running — `confirm_fixture_intact` is what catches it. It covers `small`, `medium`, `large` and `extraLarge`; `extraLarge` is iPad-only and is why `NoSpoilers-iPad` exists. **The Lock Screen families are not placeable from here and cannot be made so** — their layout is owned by PosterBoard, chronod's copy is derived and prunes anything written into it, and the only other route is synthetic clicks on the real desktop; see Phase H follow-on in `tasks/23-native-functionality-for-4-2-2.md`. See `docs/guides/building.md` and the script's own docstring, which is the long-form reference.

26. `docs/guides/brand.md` — **the cross-platform token spec**, and the authority for any visual decision. Every token with both its bindings, and an explicit note on the Swift-only families. Moved here from `docs/brand.md` on 2026-08-17, where it had been a colour-only document that the code had drifted from.
27. `NoSpoilersCore/Sources/NoSpoilersCore/Theme.swift` — the Swift binding of 26. `Palette`, `Canvas`, `Typography`, `Space`, `Radius`, `Motion`, `Icon`, plus the per-component families (`Card`, `MessageCard`, `Badge`, `Row`, `NextUp`, `Header`, `ScreenHeader`, `SectionLabel`, `DetailRow`). **`Theme.Canvas` is the only size axis** — `iosApp`, `macPopover`, `widgetSmall`, `widgetMedium`, `widgetLarge`. Do not add a second one; a `NoSpoilersCardDensity` and a `compact: Bool` both existed beside it and both are deleted. Its doc comments carry the reasoning behind each value and are worth reading before changing one.
28. `NoSpoilersCore/Sources/NoSpoilersCore/BrandPalette.swift` — the only place a colour hex lives on the Swift side. `Theme.Palette` names roles that point at it. **`signalRed` is also transcribed into three `AccentColor.colorset` JSON files**, because an asset catalog cannot reference Swift and nothing will fail to compile if they drift.
29. `NoSpoilersCore/Sources/NoSpoilersCore/SharedChrome.swift` — the shared components every target draws, and the boundary duplicated views converge onto rather than being reimplemented beside. A second implementation of anything here is a correctness issue, not a style one.
30. `scripts/alerts_check.py` — the only way to see whether the iOS session alerts reach the OS. Launches the app on the simulator and streams the `alerts` log channel back, reporting planned against pending. **Imports its device helpers from 25** rather than repeating them, the same way 23 imports 22's: two scripts that disagree about which simulator they mean is the failure this prevents. Its `--push` sample copy is *extracted from* `Strings.Alerts` in `NoSpoilersCore`, never transcribed — a second copy of notification wording would drift and still screenshot convincingly. It cannot fire one of our own alerts on demand, and its docstring carries the reason: a seeded fixture does not survive `ScheduleStore.refresh()`, and the seam that would fix it is 25's declined launch-argument trade.
31. `docs/styles.css` — the CSS binding of 26, shared by `docs/index.html` and `docs/privacy.html`. Neither page may carry its own `:root` block, a raw hex, or a raw radius.
32. `scripts/asc_write.py` — the App Store Connect session that writes, and the App Manager key id, spelled once. Split out of 23 on 2026-08-22 when it stopped being the only writer; it holds no token signing and no app lookup, because those are 22's and a second implementation of ES256 is a second thing to get wrong. Its two invariants — a 403 hint that names the key, and a write key that is not the read-only one — are asserted in 23's selftest.
33. `scripts/appstore_listing.py` — writes an App Store version's listing from `listing/<platform>/*.txt`, which is where the app's own description, keywords, promotional text, what's-new and review notes now live. **Before this the listing existed nowhere but App Store Connect**, which is how the macOS keywords kept `F1,Formula 1` for nine days after the sweep that was meant to remove them: the sweep edited four surfaces by hand and there was no fifth place to look. It refuses to write copy carrying the owned terms, using 22's `trademark_hits` — the same check 22 reports under NEEDS YOU, so a listing cannot pass here and be flagged there. It creates the version record, writes the four fields and the review detail, and attaches a build. **It never submits**; a READY_FOR_SALE version is not even a candidate, so it cannot rewrite words that are already on the store.
34. `scripts/mac_screenshots.py` — the macOS listing screenshot: drives the installed app, clicks the status item through System Events and captures a top-right region of the real screen. **It no longer seeds a fixture.** It did, and the sandboxed Mac app could neither read nor replace a file an unsandboxed script wrote into its group container — so the seed was invisible and it displaced the cache the app maintains, which then failed to load and failed to save for a day before anyone read the log. Making it work needs the app to be told what to hold, which is the offline seam 25 declined to open. **It refuses two things**, both learned by doing them: photographing a build that is not the one this checkout makes — the first run captured the installed 1.0.21 and produced a perfect screenshot of the wordmark deleted for 4.1(a) — and running with the feed reachable, which makes the picture one of today rather than of the fixture. Which data it captured comes from the app's `store` log channel, not from reading the cache back, because that was wrong on both of the first two runs.

35. `NoSpoilersCore/Sources/NoSpoilersCore/FeaturedSession.swift` — **the one answer to "what is on, or on next"**: the session running, or the next to start. Third planner in the shape of 27's neighbour `TimelinePlanner`, after `SessionAlertPlanner`, and pure for the same reason — `now` is a parameter, so every decision is assertable. It computes no boundary of its own; `ScheduleBoundaries` is the single traversal and `SessionResolver` the single answer to when a session starts and is over. **Two callers, deliberately one implementation**: the Live Activity and `NextSessionIntent` both say this sentence, one on a Lock Screen and one out loud, and two functions computing it would be two answers a user could catch disagreeing on the same device. `lookAhead` is caller-owned because the two genuinely differ — 8 hours for an activity, `.infinity` for an intent — the same split that puts `maxEntries` in the widget and the 64-notification cap in the scheduler.
36. `NoSpoilersCore/Sources/NoSpoilersCore/ScheduleSnapshot.swift` — the App-Group-cache-then-network read, for the processes that wake up with nothing in memory. Was `resolveWidgetData`, private inside `NoSpoilersWidget.swift`, for as long as the widget was the only such process; the App Intent is the second, and a copy beside the original would have been two answers to where the schedule comes from. `ScheduleStore` is the app's path and stays separate: it publishes, refreshes on a timer, and belongs to a process with a lifecycle. **It writes a successful fetch back to the cache**, which is the trap 25's `confirm_fixture_intact` exists to catch.
37. `NoSpoilers/NoSpoilersWidget/SessionActivityWidget.swift`, `NoSpoilers/NoSpoilers/SessionActivityController.swift` and `SessionActivityAttributes.swift` in Core — the Live Activity. The attributes type is in Core because ActivityKit matches a running activity to its configuration by type identity, so the app and the extension must share one declaration; a copy in each compiles and never renders. The controller is thin for the same reason `SessionAlertScheduler` is — every decision is in 35 — and is `#if os(iOS)` on the Core side because the package builds for macOS too. **No entitlement and no prompt**: `NoSpoilersApp.entitlements` still carries only the App Group, and only push-to-start would need more. The app target gains `INFOPLIST_KEY_NSSupportsLiveActivities`.
38. `NoSpoilers/NoSpoilers/NextSessionIntent.swift` — the App Intent behind Siri, Spotlight, Shortcuts and the Action button, plus the `AppShortcutsProvider` that makes it discoverable without the user opening Shortcuts first. **Its install-time copy is the one exception to the strings rule**, and not by choice: `appintentsmetadataprocessor` extracts the title, description, short title and phrases at build time and fails the build on anything that is not a literal at the declaration site. Those four are inline with a comment saying so, and `Strings.Intents` carries a note pointing at them; what the intent says at *run* time is not extracted and lives in `Strings.Intents` with everything else. Verify extraction by reading `Metadata.appintents/extract.actionsdata` out of the built `.app` — "Extracted no relevant App Intents symbols" in the build log means the intent is not there.

**Never identify an Xcode Cloud product by name or by a recorded id.** The name is the field the fault rewrites, and the id does not survive a deletion — a constant id took 23 down entirely, dry run included. `find_ci_product` matches on the app the product builds, which is the field the fault strips rather than forges, so a seized record matches nothing instead of matching wrongly.

## Current repo state

- The application architecture is still forming.
- `NoSpoilersCore` is the shared Swift package for domain logic and tests.
- `NoSpoilersApp`, `NoSpoilersWidgetExtension`, and `NoSpoilersMac` are the Xcode project targets.
- The shared `NoSpoilers` scheme currently builds the macOS app; the iOS wrapper uses the `NoSpoilersApp` scheme when present in shared schemes.
- The control plane above is the authoritative source for implementation standards.

## Update rule

When core architecture or canonical patterns change, update this guide so Claude has an accurate map of the approved structure.
